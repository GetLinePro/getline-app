# Отделение GetLine от CMFA — журнал решений и статус

Зачем всё это: GetLineVPN — форк ClashMetaForAndroid. Цель работ — довести продукт до
состояния, в котором CMFA можно обновлять с upstream, не разгребая конфликты по всему
дереву. Не «идеальная архитектура», а обновляемость.

Спецификации срезов лежат рядом: `slice-*.md`, `step-*.md`.

---

## Проверенные факты о форке

Установлено сравнением с `upstream/main` @ `82b73a4b` (v2.11.32).

- **Диф от upstream: 480 файлов** — 236 R (переименования), 132 A, 98 M, 14 D.
- **Полное переименование namespace в `pro.getline.vpn.*` было не нужно.** Upstream уже
  поддерживает свой applicationId: `build.gradle.kts` читает `custom.application.id` из
  `local.properties`, при этом namespace библиотек остаётся `com.github.kr328.clash.*`.
  Цена ошибки — 236 переименований плюс переименование JNI-символов в
  `core/src/main/cpp/main.c` (`Java_com_github_kr328_...` → `Java_pro_getline_vpn_...`).
- **Модули CMFA не самодостаточны.** Ни один из `core`/`service`/`common`/`design`/`app`
  не содержит своей `android {}` — namespace, flavors `alpha`/`meta`, compileSdk, signing,
  dataBinding, NDK/ABI задаются в корневом `subprojects {}`. Нет `buildSrc`, нет
  convention-плагинов. Подключить CMFA как набор из трёх библиотек нельзя — только весь
  build целиком.
- **`service` рассчитан на чужой applicationId** — `${applicationId}` в манифесте
  (`service/src/main/AndroidManifest.xml`, 5 мест).
- ~~**Продуктовый UI живёт внутри форкнутого `:design`**~~ — было верно до среза 4.
  После него диф `:design` от upstream упал с ~5165 до 1393 строк, и остаток — это
  ребрендинг CMFA-экранов (styles +201, themes +71, `getline_brand` +60, шрифт, логотип),
  а не продуктовый UI. Основной источник конфликтов теперь — переименование namespace,
  см. «Пересмотр порядка после среза 4».
- **Лицензия: GPLv3** (CMFA и Mihomo). Распространяемый клиент должен быть
  GPL-совместимым, исходники доступны получателям. Серверная часть, биллинг,
  инфраструктура, ключи и бренд этим не затронуты.

## Решения

Приняты в ходе работ. Не пересматривать без причины — у каждого есть основание.

### 1. Advanced — диагностический интерфейс, не продуктовая навигация

Остаётся: кнопка только в DEBUG (`GetLineOnboardingActivity` →
`design.setAdvancedButtonVisible(BuildConfig.DEBUG)`), скрытый люк из 7 тапов по бренду
(`GetLineOnboardingDesign.onBrandTitleClicked`), маршрут `MainActivity.EXTRA_OPEN_ADVANCED`,
метод `GetLineNavigation.openAdvanced()`.

Из продуктового контракта удалены `openServerSelection()` и `openProfiles()` — у них было
ноль вызовов. `openAdvanced()` — не мёртвый контракт, его удалять нельзя.

### 2. `common` разрешён продуктовому коду, `core` и `service` — нет

Диф `pro.getline.vpn.common.*` от upstream — чистое переименование пакетов. Риск конфликта
при bump близок к нулю, поэтому `ticker`, `log.Log`, `store.Store`, `compat.*` остаются
доступными. Гейт `common` не проверяет — это решение, а не дырка в регексе.

### 3. Продуктовые модели живут в `:getlineui` (закрыто срезом 4)

Раньше модели делили `:design` с CMFA UI, потому что `app` видит `design`, обратно — нет.
После среза 4 `GetLineProductState`, `GetLineRecoveryAction`, `GetLineTraffic` и остальной
продуктовый UI — в `pro.getline.vpn.getlineui.*`. `:getlineui` не зависит от `:design`.

### 4. Форматтер трафика скопирован дословно, включая странность

`design/util/TrafficFormat.kt` — копия приватной `trafficString` из `core/util/Traffic.kt`:
целочисленное деление, затем `data.toFloat() / 100`. Выглядит багом. **Это текущий вывод на
экране.** «Починка» молча меняет UI. Не трогать без отдельного продуктового решения.

### 5. `onStopped` — принятое изменение поведения

`BaseActivity` показывал `showExceptionToast(ClashException(cause))` — тип из `core.bridge`.
Home его перекрывал продуктовым тостом, Onboarding наследовал CMFA-вариант.
`GetLineActivity` реализует вариант Home для обоих экранов. Onboarding получил продуктовый
тост вместо CMFA-исключения — **это принято, не регрессия**. `ClashException` в продуктовый
код не тянуть.

### 6. `CMakeLists.txt` не минимизируется

Переписан относительно upstream намеренно: upstream вызывал `git submodule foreach` из
неправильного `WORKING_DIRECTORY`, плюс добавлены `-ffile-prefix-map` (воспроизводимость) и
генерируемый `getline_native_version.h`. Конфликт при bump — один файл, ~10 минут.
Разрешать в пользу нашей версии.

### 7. Legacy CMFA Activities остаются до среза 5

~20 экранов (`ProfilesActivity`, `ProxyActivity`, `SettingsActivity`, `LogsActivity`,
`PropertiesActivity`, `*SettingsActivity`, …) продолжают жить в `app` и наследовать
`BaseActivity`. Им импортировать `core`/`service` **разрешено** — они не в периметре гейта.
`BaseActivity.kt` не менять: на нём стоят все они.

### 8. Гейт проверяет не только импорты

`scripts/check-product-boundary.sh` — две проверки. Только по `import` недостаточно:
`uiStore.proxySort` даёт тип `core.model.ProxySort` без единого импорта (Kotlin выводит его),
и такая утечка проходит незамеченной. Вторая проверка — по голым идентификаторам.

При изменении гейта обязательно доказывать, что он **падает** на искусственно внесённой
утечке. Зелёный скрипт, который ничего не ловит, хуже отсутствия скрипта.

### 9. Проприетарный клиент — отдельный продукт, не бесплатная страховка

Текущая линия на CMFA/Mihomo — GPL, клиент открытый. Закрытый white-label потребует замены
VPN runtime (кандидат — Xray-core под MPL 2.0) и оценивается отдельно. Ребрендом нынешнего
форка это не делается. Архитектурная граница `product ↔ VpnRuntime`, которую строят эти
срезы, оставляет такую возможность открытой — но специально под неё сейчас ничего не пишем.

### 11. Данные приложения не покидают устройство; переустановка начинается с нуля

Симптом: после переустановки приложение открывалось на Home («я вошёл»), а таб подписки
писал «Управление подпиской недоступно».

Причина — два разных критерия «пользователь вошёл»: роутинг смотрел на `hasImported()`
(`MainActivity.resolveLaunchTarget`), таб подписки — на `hasSession()`. Auto Backup
восстанавливал `files/imported`, `files/pending` и базу `profiles`, но не зашифрованное
хранилище сессии — оно исключено намеренно, и его Keystore-ключ восстановление всё равно
не переживает.

Не регресс срезов: механика существует с `d3ed62a3` (27.07.2026), раньше не проявлялась,
потому что Auto Backup пишется не мгновенно.

**Отвергнутое решение**: развести состояния в роутинге (`ProductEntryPolicy`: Home только
при сессии или managed-биндинге). На диске «восстановленный сирота» и «профиль, руками
импортированный через Advanced» побайтово неразличимы — биндинг пишут только продуктовые
пути (`GetLineOnboardingActivity`, `GetLineHomeActivity`), CMFA-импорт не пишет его никогда.
Политика уводила бы в Onboarding и второй случай, хотя Home его поддерживает осознанно:
`ActiveProfilePolicy` бережёт Advanced-выбор, а `GetLineHomeDesign` рисует отдельное
состояние `SignedOut`. Отличить их маркером можно было бы только записав его в момент
CMFA-импорта — то есть правкой апстримных файлов, диф с которыми обнулён срезами 7a/7b.

**Принято**: чинить источник, а не следствие. `android:allowBackup="false"`,
`full_backup_content.xml` возвращён к апстримному виду (атрибут больше не ссылается на него),
`data_extraction_rules.xml` исключает все домены из device-to-device переноса.
`allowBackup=false` закрывает облачный бэкап на всех версиях, но **не** закрывает D2D на
Android 12+ — поэтому правила остаются нужны. Пустой блок означал бы «переносить всё»,
поэтому домены перечислены поимённо.

Второй довод, сам по себе достаточный: профиль подписки перечисляет серверы, к которым
подключается пользователь. Для VPN в юрисдикции, где он не вполне легален, отдавать это
в облачный бэкап нельзя.

После этого `hasImported()` снова корректный признак: восстанавливать нечего, а выход из
аккаунта и так удаляет конфигурацию. Роутинг `MainActivity` остаётся апстримно-простым.

Цена: переустановка теряет профиль и у пользователя с подпиской по ссылке без аккаунта —
ссылку придётся ввести заново. Теряются и настройки (тема, список приложений в access
control). По решению 10 это приемлемо.

Не проверено: что механизмом был именно Auto Backup. Вывод сделан из правил бэкапа и из
«раньше так не было», логами `bmgr` не подтверждён.

98 изменённых upstream-файлов — это и есть остаточная конфликтная поверхность:
`design` 31 (ребрендинг CMFA-экранов), `service` 22, `core` 11, `common` 1 (тег лога),
остальное в `app`. Всё это — содержательные правки, каждая с причиной.

Проверка на смоделированном upstream-коммите (правка в `import`-блоке
`ProxyDesign`, `MainDesign`, `MainActivity`, `ProfileManager` поверх `upstream/main`,
слияние через `git merge-tree`):

- на состоянии до работ — конфликт в `MainActivity.kt`, три файла слились с автослиянием;
- на текущем — ни одного конфликта, ни одного автослияния.

Оговорка: git и раньше вытягивал часть переименований через rename detection. Выигрыш не в
том, что каждый из 218 файлов конфликтовал бы, а в том, что слияние больше не опирается на
эвристику, которая ломается при крупных правках upstream и отказывает, если upstream сам
двигает файл.

Срез 3 попутно вернул `PropertiesActivity` и `PropertiesDesign` к upstream с точностью
до переименования пакетов и убрал единственное исключение из гейта границы.

### Порядок и почему он такой

Извлечение модуля — **следствие**, а не первый шаг. Пока продуктовый экран наследует
CMFA-базу и тянет `design.R`, перенос файлов в новый модуль не уменьшает связанность, а
только двигает мебель. Сначала рвутся конкретные зависимости, потом переезжает то, что уже
свободно.

Уточнение по 6: убрать `app → :design` нельзя, пока legacy CMFA Activities живут в `app`
(решение 7). То есть 6 блокирован **срезом 5**, а не 4.

### Пересмотр порядка после среза 4 (принято)

Шаг 7 стоял последним с обоснованием «не переименовывать то, что потом удалим при 5/6».
Обоснование отозвано: срез 5 отложен бессрочно (решение 1 — Advanced нужен как диагностика),
6 блокирован пятым, а конфликты приходят с каждым bump. Экономия, ждущая бессрочно
отложенного среза, не окупается.

Замер после среза 4: **218 из 237 изменённых файлов отличаются от upstream ровно на
`package`/`import`** — `design` 86, `service` 49, `app` 39, `core` 22, `common` 22.
Это главный оставшийся источник конфликтов.

Шаг 7 разделён по признаку «есть ли в модуле компоненты манифеста». AGP резолвит
`android:name=".Foo"` по namespace, а не по applicationId, поэтому смена namespace у
`app`/`service` меняет `ComponentName` у установленных приложений и ломает ярлыки,
плитку Quick Settings, always-on VPN и `componentEnabledSetting` для «скрыть иконку».
Компоненты есть только в этих двух модулях — проверено.

- **7a** — `common`, `core`, `design`, `hideapi`: 130 файлов.
- **7b** — `app`, `service`: 88 файлов.

Разделение сохранено только как порядок работ: 7a уже был в исполнении, когда выяснилось,
что отсрочка 7b не нужна. Единым срезом было бы не хуже.

### 10. Установленной базы нет — совместимость не ограничивает решения

Приложение — альфа возрастом в считаные дни, пользователей двое (автор и заказчик),
переустановка с потерей локального состояния приемлема.

Отсюда: не закладывать миграции состояния и не дробить срезы ради сохранности
`ComponentName`, ярлыков, always-on VPN, QS-плитки и `SharedPreferences`. Именно на этом
основании снята отсрочка 7b: смена `ComponentName` ломает перечисленное, но ломать нечего.

Вернуть вопрос о совместимости при подготовке публичного релиза.

## Что осталось из зависимостей продукта от `:design`

Срез 4 вынес продуктовый UI в `:getlineui` (экраны, модели, layouts, строки, тема
`GetLineTheme`, `GetLineUiStore`). `app → :design` **ещё нужен** — legacy CMFA Activities
(решение 7) живут в `app` до среза 5; убрать `app → :design` — содержание среза 6.

Продуктовые Activities могут по-прежнему тянуть отдельные `design.R` строки для CMFA-only
ресурсов (например `unable_to_start_vpn`, `new_profile`); продуктовые `get_line_*` — в
`getlineui.R`.

## Регулярные проверки

```bash
scripts/check-product-boundary.sh      # граница продукт ↔ CMFA
scripts/verify-mihomo-gate.sh          # no_ssh реально исключает SSH
./gradlew :app:assembleAlphaDebug :app:testAlphaDebugUnitTest
```

Ручное на устройстве после каждого среза, автоматикой не покрыто: строки трафика, таймер
сессии, список серверов и health check, переключение табов и back, вход/OTP в онбординге,
7 тапов по бренду, DEBUG-кнопка Advanced.
